## 3. 现栈（MVP v0.2）能力边界

**可直接承载**（无需换件）：

- 2D 底图漫游/拖拽/缩放、离线瓦片、暗色窗口壳、菜单工具栏、便携分发
- 生命周期管理（拉起/健康检查/级联退出）→ 天然对应"启动加载界面 + 一键自检"的骨架
- `/api/map/config` 配置驱动 → 可扩展为"场景配置驱动"（T0 场景选择本质是换配置）

**必须扩展**（方向不变、加零件）：

- deck.gl 动态叠层（轨迹/热区/锁定框）、3D（terrain/fill-extrusion/Tile3D/室内自研图层）
- MQTT 实时消息总线（遥测/链路指标/事件驱动 UI）
- 视频网关 + 播放器、离线语音服务栈（ASR/TTS）、AI 决策服务模块
- 设计 tokens + 状态管理（Zustand）+ 图表库（ECharts/antv G6）
- 数据层：SQLite → PostGIS + 时序库；报告生成

**可能必须重选**（首轮确认后风险解除）：

- ~~终端平台若为 Android 平板~~：**已确认非 Android**（Windows → 国产化麒麟/统信 ARM64），Electron 路线成立。剩余风险 = 国产化 OS 兼容性需真机验证（GPU 驱动、Chromium 表现、软渲染性能），属测试风险而非架构风险。

## 4. 关键长期决策点（选项 → 建议 → 与 MVP 的联动）

### K1 终端平台与壳 ✅ 已确认（首轮）

**Windows 先行实现与跑通；二期移植国产化平板（麒麟/统信 + 飞腾/鲲鹏 ARM64）。**

- 非 Android → **Electron 路线锁定**（官方 linux-arm64 二进制；麒麟/统信均为 Debian 系，可出 deb）
- 壳层仍按"可替换模块"实现（成本极低，保留未来灵活性）
- 二期真机验证点：GPU 驱动可用性、无 GPU 时软件渲染性能、Chromium 在国产化 OS 上的稳定性
- 剩余待定小项：具体平板型号与 CPU（飞腾 / 鲲鹏）、OS 版本（麒麟 V10 / 统信 UOS）——只影响测试矩阵，不影响架构

### K2 三维渲染路线 ✅ 已确认需 2D/3D 切换 → 锁定路线 A

- **路线 A（已锁定）**：MapLibre 为底，逐级加 3D——`terrain`（raster-dem 地形）+ `fill-extrusion`（OSM 建筑矢量挤出）+ deck.gl `Tile3DLayer`（3D Tiles：倾斜摄影/建筑模型）+ 自研室内楼层图层（deck.gl 自定义 layer：楼层/房间/人员位置）
- ~~路线 B（CesiumJS 为底）~~：2D 模式体验退化、包体更大、与现 MVP 不兼容 → 出局
- ~~路线 C（2D MapLibre + 3D Cesium 双引擎）~~：维护成本双倍 → 出局

**2D/3D 切换实现**：同一 MapLibre 实例内切换——2D = pitch 0 + terrain 关闭；3D = pitch 倾斜 + terrain/fill-extrusion 开启。单引擎双模式，免维护两套底图，与"2D/3D 切换"需求天然对齐。

**判定依据**：需求是"区域级地形 + 城市级建筑 + 重点单体室内"，不是全球级球体 → 路线 A 成立。
**数据侧（第三轮确认）**：地形 DEM **十几米级即可**——SRTM GL1 / ALOS AW3D30（30m）免费易得且满足要求，如需更细再评估 12.5m 级产品；建筑默认 OSM 矢量挤出起步，倾斜摄影/BIM 仅重点区域按需；**室内楼层数据当前无需求**（自建 JSON 楼层模型保留为后续升级选项，不阻塞）。
**联动**：MVP 瓦片目录预留 `dem/`、`3dtiles/`、`vector/` 子目录；前端目录预留 `layers/`（deck.gl）骨架。

### K3 实时消息总线 ✅ 已确认（第三轮）：MQTT 作为内部消息总线

**定位（已厘清）**：MQTT **不是无人机链路协议**，是**系统内部消息总线**——链路侧的"数据链 + UDP 组播"由桥接服务（C++/Java）接收解析后，发布到内部 MQTT broker，供 Java 服务、AI 模块与前端（mqtt.js over WebSocket）订阅。

```
无人机（数据链 + UDP 组播）──> 桥接服务 ──> 内部 MQTT 总线 ──> Java / AI / 前端
      （链路协议，外部）                    （系统内发布订阅，已确认）
```

- 选型：EMQX（云/边，支持 MQTT over WebSocket 直供前端订阅）/ NanoMQ·Mosquitto（端侧轻量）；遥测、链路指标、AI 事件统一走 topic
- 关键红利：**遗嘱消息（Last Will）天然对应"无人机失联检测"**
- 引入节奏：MVP 阶段可暂不部署 broker（单机直连即可），P1 上实时遥测时正式引入

**联动**：MVP 阶段**冻结 topic 命名规范**（如 `telemetry/uav/{id}/pos`、`ai/plan/recommend`），把消息契约与接口契约一并作为长期资产。

### K4 视频流

- 网关选型：**ZLMediaKit（建议）**——C++ 高性能、GB28181/RTSP 拉流 → WebRTC/WS-FLV 分发，国产开源，与团队的 C++ 背景契合；Java 侧仅做信令与权限
- **已确认参数（第二轮）**：编码 **H.265**、端到端延迟 **≤0.5s**；路数、分辨率仍待定
- **H.265 处理策略**：Chromium 不原生解码 H.265 → 网关 FFmpeg **转码 H.265→H.264**（硬件编码或 ultrafast 预设，0.5s 预算内可行）；WebCodecs HEVC 直解仅作备选实验（平台相关，风险高）
- 播放：WebRTC（低延迟首选，0.5s 预算安全）；WS-FLV（次之，延迟接近上限）；HLS（不可用，延迟超标）

### K5 离线语音（ASR/TTS）

| 部件 | 候选 | 特点 |
|---|---|---|
| ASR | sherpa-onnx（流式、C++、ARM64 优化，建议先验） | 开源可控；中文用 paraformer 系模型 |
| | Whisper（whisper.cpp） | 准但重，平板算力吃紧 |
| | FunASR / Vosk / 讯飞离线 SDK | 中文优化或商用（含 NPU 适配） |
| TTS | piper（建议） | 快、离线、多音色 |
| | espeak-ng / 讯飞离线 | 机械音 / 商用 |
| VAD/唤醒 | webrtcvad + 阵列降噪 | 依赖平板麦克风硬件能力 |

**已确认（第二轮）**：指令集为**有限范围**（"推荐任务模式""选择最优方案"等短指令）、**必须离线识别、不依赖在线服务**；平板麦克风能力未知（降噪/阵列能力待真机验证）。
**意图理解**：指令集有限 → **规则匹配为主**；自然语言泛化需求时再加本地小模型（Qwen 0.5–3B，llama.cpp/ONNX int8），全程离线。
**联动**：语音做成独立 sidecar 服务（C++ 实现），与 UI 经事件总线解耦——对应"模块加载进度"中可独立启停的模块。

### K6 AI 决策引擎

- **已确认（第二轮）**：推荐规则**已有业务规则可固化** → 层 1 规则引擎起步成立；本地模型**先跑 Windows 10 开发机**（用户本机），平板算力未知
- 层 1（P2 起步）：**规则引擎**——方案生成、威胁评级、优先级排序、覆盖率估算先规则化，可解释、可审计（"人在回路"对可解释性有硬要求）
- 层 2（P3）：本地推理（ONNX Runtime / llama.cpp 小模型）——态势摘要、语音理解；**模型规模按开发机 CPU/GPU 实测确定**（无独显时 q4/int8 量化小模型仍可跑）
- 层 3（P4）：云边协同——云端策略模型下发、边缘本地执行（正对应需求中"云端策略模型下发边缘节点"的表述）；平板侧算力未知，部署形态待真机评估
- 接口形态：决策服务 = 输入态势 JSON → 输出方案 JSON，算法可替换

### K7 后端形态与数据（sidecar → 云边端）

```
端侧（平板）：UI 进程 + 本地服务进程（现 sidecar 演进而来）
            ——本地缓存、离线可用、断链续行的"最后阵地"
边侧（前沿指控单元）：数据汇聚、区域服务、边缘推理
云侧（后方算力中心）：全局一致性校核、大模型、历史库
```

- 存储：端 SQLite（任务状态/缓存）；边·云 PostGIS（空间数据）+ 时序库（遥测：TDengine 国产友好 / TimescaleDB）
- 断链续行 = **事件溯源式同步**：本地事件队列 + 恢复后对账合并；服务按"幂等 + 可重放"设计
- 联动：MVP 的 API 加 `/api/v1` 版本前缀；sidecar 内部分模块化（对应启动自检的五项模块：地图引擎/通信链路/AI 引擎/集群管理/数据服务，每模块一个 health 子项）

### K8 C++ 的角色 ✅ 已确认（首轮）

**C++ 不强制，但性能敏感处优先采用 C++ 资产**（如 FFmpeg 视频流转码）——团队 C++ 背景作为可选武器，而非硬约束。

| C++ 天然归属 | 落位 |
|---|---|
| 视频流处理（FFmpeg 转码/推流） | ZLMediaKit 内置 FFmpeg 链路（H.265→H.264、RTSP→WebRTC）；若倾向 Java 侧集成可用 JavaCV（FFmpeg 的 Java 封装）作过渡，但性能关键路径仍建议原生 C++ 链 |
| ASR/TTS 推理（sherpa-onnx/whisper.cpp）、雷达/电子信号处理、MAVLink/自组网协议栈、图像识别前处理（OpenCV） | 独立 C++ 服务进程 + MQTT/REST 通信（**建议**，与 Java 解耦） |

分工原则：**C++ 做感知/通信/媒体，Java 做业务/流程/持久化，React 做界面，消息总线为界**。

### K9 UI 设计系统与性能

- 设计 tokens（色板/间距/字体/发光效果）第一时间冻结；组件库建议 Tailwind + 自研组件（毛玻璃卡片等），AntD 可作基础件但军事风质感需深度定制
- **性能红线**：地图/轨迹/热力图全部走 WebGL canvas（deck.gl），React 只管 DOM 面板；渲染分区隔离，杜绝 React 重渲染拖累地图帧率
- 状态管理：Zustand（store 模式，与模板 `@accelint/core` 思想一致）；事件驱动：消息总线 → 事件 → store → UI 联动（语音/遥测触发的界面变化都走这条路）
- 图表：ECharts（指标曲线）+ antv G6（链路/云边端拓扑图）

### K10 安全与国产化 ✅ 已确认非涉密（首轮）

- **项目非涉密**：不涉及分保/保密要求，开源选型空间大；安全按常规基线执行（身份鉴别、审计日志、传输加密 TLS）即可；国密 SM2/SM3/SM4 降级为可选项（BouncyCastle / sm-crypto），非强制
- 国产化组合友好选型不变：JDK（OpenJDK/毕昇 ARM64）、时序库 TDengine、消息 NanoMQ/EMQX、网关 ZLMediaKit 均可在麒麟/统信 ARM64 运行
- 仍保留：依赖锁定清单（pnpm-lock + Maven 依赖清单）——为国产化平台适配与后续可能的合规审查备档

## 8. 结语

需求初稿揭示的终态是"三维态势 + 实时协同 + 离线智能"的完整系统，MVP 只是它的地基。本文档的核心判断：

1. **现栈方向正确，无需推倒**：React + MapLibre（+deck.gl）+ Java + 桌面壳，正是承载这个终态的业界主流组合（模板 Accelint 即为同类先例）
2. **三个必须提前预埋的地基**：deck.gl 图层体系、MQTT 消息契约、壳层多模块编排——这三样不预埋，P1 就要返工
3. **平台与总线路线已锁定**：Windows 先行 → 国产化麒麟/统信 ARM64，Electron 全程成立；MQTT 内部总线已确认；视频路数/分辨率、云边端边界、平板型号暂缓不阻塞
4. **C++ 定位已明确**：不强制，但视频流（FFmpeg）、语音推理、信号处理等高性能处优先用 C++ 资产，与 Java/React 以消息总线为界各司其职

MVP 真正的验收标准可以再加一条：**这份探讨稿里的预留项，在 P0 交付时是否都已就位**——那才是"最小走通"对"完整系统"的价值。
