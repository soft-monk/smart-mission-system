# AI（Codex/Agent）协作开发规范与文档体系指南

> 适用项目：任务管理系统（需求文档见同目录 `任务管理系统界面需求文档.md`）
> 方法论来源：[Codex 开发程序 一次全部讲明白（技术胖）](https://jspang.com/article/46)
> 核心结论：**文档是 Agent 的唯一契约**。Agent 不会"猜"，所有文档没写清的地方，它都会自由发挥——把发挥空间提前收进文档，犯错空间就收进笼子。

---

## 1. 回答你的五个问题（速览）

| 问题 | 结论 |
| --- | --- |
| 需要提供什么文件？ | 需求文档 + 设计文档 + 任务清单 + 验收标准 + `AGENTS.md` + 变更/决策记录，全部纳入 Git |
| 需要控制哪些关键？ | 权限模式、计划先行、最小改动、diff 三问、验证闭环、界面文案一致性、待确认事项人工裁决 |
| 需要控制哪些流程避免 agent 犯错？ | 五步循环 + 三道门禁（计划确认门 → 验证门 → 验收门），高风险操作先解释后执行 |
| 怎么持续迭代且可回溯？ | 小步提交 + 提交信息挂需求编号 + 文档版本化 + 决策记录（ADR）+ 里程碑 tag |
| 需要需求/设计文档吗？要多细？ | **都需要**。细到"每条需求都能被验证、每个选择都被规定或授权"的程度；用 MUST/SHOULD/MAY 分级 |

## 2. 文件体系：项目里需要提供哪些文件

### 2.1 推荐目录结构

```
project/
├─ docs/                          # 文档库（与代码同仓、同步版本）
│  ├─ 01-需求文档.md               # 已有：任务管理系统界面需求文档.md（What）
│  ├─ 02-设计文档.md               # How：架构、技术选型、UI/交互规范、数据与接口契约
│  ├─ 03-任务清单.md               # 可执行的任务分解，带编号
│  ├─ 04-验收标准.md               # DoD：每个任务的完成定义
│  ├─ 05-变更记录.md               # CHANGELOG：需求/设计变更台账
│  └─ decisions/                  # 轻量决策记录 ADR
│     └─ 0001-场景名称统一为集群协同攻击.md
├─ AGENTS.md                      # 给 Agent 的项目规则（最关键的文件）
├─ FilesTree.md                   # 项目结构说明（让 Agent 先读懂项目）
├─ .codex/
│  ├─ hooks/
│  │  ├─ hooks.json               # 危险命令拦截、提交前校验
│  │  └─ check_command.py
│  └─ skills/                     # 复用流程：需求核对、UI 验收等
├─ src/                           # 代码
├─ .gitignore
└─ README.md                      # 人类入口：如何跑起来、文档索引
```

### 2.2 每个文件的作用与责任

| 文件 | 回答的问题 | 谁维护 | 更新时机 |
| --- | --- | --- | --- |
| 需求文档 | 做什么（界面、文案、交互、按钮、状态色） | 人工（产品） | 需求变化时；Agent **不得自行修改** |
| 设计文档 | 怎么做（架构、组件、接口、数据结构、样式规范） | 人工审定，Agent 可起草 | 技术方案变化时；与需求编号对应 |
| 任务清单 | 按什么顺序做（每项带需求编号，如 `R-场景1-T4-界面2`） | 人工拆分或 Agent 起草后人工确认 | 每轮迭代前更新 |
| 验收标准 | 做到什么程度算完成（可勾选、可测试） | 人工 | 与需求文档同步 |
| AGENTS.md | Agent 必须遵守的规则与命令 | 人工 | 踩坑后立即补充（防复发） |
| 变更记录 | 改了什么、为什么、何时（文档级 diff） | 每次变更随手记 | 需求/设计变更时 |
| 决策记录 ADR | 有争议的决策及理由（如"集群协同突击 vs 攻击"） | 人工裁决后记录 | 争议解决时 |
| 开发日志 | Agent 每次任务做了什么、验证结果 | Agent 每次任务后追加 | 每次任务 |

> 原则：**需求文档、设计文档、AGENTS.md 只有人工能改**。Agent 发现问题可以提出建议，但落地必须人工批准。这就是"请求批准"权限模式在文档层面的体现。

## 3. 需求文档、设计文档需要多细？

### 3.1 结论：需要，而且要细到"无歧义、可验证"

LLM 不会追问，遇到文档没写的细节会自行发明。文档的细致程度直接决定 Agent 的出错率。

### 3.2 需求文档的粒度要求（对照现有文档的差距）

现有 `任务管理系统界面需求文档.md` 已经达到较高水平，补齐以下内容即可：

1. **每条界面需求都要带验收标准**（可勾选），例如：
   > 界面：T4 目标详情界面（场景1）
   > 验收：□ 显示目标编号/威胁等级/坐标/来源四字段 □ 目标003点击后地图高亮 □ 底部有【持续跟踪】【加入打击候选】两按钮
2. **待确认事项必须人工关闭**。现有文档第 10 节的 7 条（如"集群协同突击 vs 集群协同攻击"、场景一 T7 缺按钮）是**最高优先级人工任务**——凡属此类，Agent 一律不得自行拍板，应停止并提问。
3. **示例数值要标注性质**。"打击成功率92%""边缘自主执行率87%""目标003"标注为"演示数据，由系统实时计算生成"，否则 Agent 可能写死。
4. **文案即契约**。界面所有中文文案（语音台词、按钮文字、状态短语）从需求文档原文引用，Agent 不得润色、改写、省略。核对方式见 5.4 节。

### 3.3 设计文档的粒度要求（需要新建）

需求文档回答 What，设计文档回答 How。至少包含：

| 章节 | 内容 | 粒度要求 |
| --- | --- | --- |
| 技术选型 | 框架、语言、UI 库、构建工具 | 精确到版本 |
| 目录结构 | src 下每个目录的职责 | 逐目录说明 |
| 组件清单 | 每个界面/组件的实现位置与命名 | 映射到需求编号（R-ID） |
| 数据结构 | 目标、集群、方案等实体的字段与类型 | 字段级 |
| 接口契约 | 与后端/仿真系统的数据交互（如语音、地图数据） | 请求/响应级 |
| 交互规范 | 状态色、布局、动画触发条件（对应需求文档第 3 节） | 规则级，可测试 |
| 错误与边界处理 | 无数据、自检失败、语音未识别等 | 每种异常一个处理策略 |

### 3.4 分级写法：MUST / SHOULD / MAY

文档统一用三级限定词，杜绝"可能、大概"：

- **MUST（必须）**：Agent 必须实现，验收必查项。如"T4 目标列表必须显示目标编号/威胁等级/坐标信息/来源四字段"。
- **SHOULD（应该）**：默认实现，若有理由偏离需在决策记录里说明。
- **MAY（可选）**：Agent 可自行决定，但要记录选择。

## 4. 关键控制点（防止 Agent 犯错）

### 4.1 权限模式（第一步防线）

按 jspang 文章的映射：

| 阶段 | 权限模式 | 理由 |
| --- | --- | --- |
| 陌生项目/首轮探索 | 请求批准 | 每个关键动作（改文件、跑命令、访问敏感位置）先问 |
| 日常开发（当前项目内） | 替我审批 | 项目内常规动作放行，项目外/网络/高风险仍需确认 |
| 完全访问权限 | **本类项目不建议** | 任务系统涉及大量文件与脚本，风险高于收益 |

> 权限越高效率越高，但越强的工具越需要边界感。生产/重要仓库永远不要开完全访问。

### 4.2 计划先行（第二步防线）

jspang 文章的核心习惯：**先给计划，不要直接开发**。

- 每次任务第一句话："请先给出计划，列出要修改的文件、改动点、验证方式，**不要开始改代码**。"
- 人工确认计划方向无误后才说："按计划执行，保持改动最小化，不做无关开发。"
- 计划里出现无关重构、自行增删功能、改写需求文案 → 立即纠正，比事后回滚便宜得多。

### 4.3 改动最小化（第三步防线）

- 一个任务只解决一个需求点；能改一处不碰十处；能修 bug 不重写架构。
- 禁止"顺手优化"：任何计划外改动必须单独提出、单独批准。

### 4.4 diff 三问（第四步防线）

每次改动后必须查 diff，只问三件事：

1. 改动范围是否合理？
2. 是否只解决当前问题？
3. 有没有无关重构或风险操作？

### 4.5 验证闭环（第五步防线）

jspang 文章的循环：**找命令 → 运行 → 解释结果 → 继续修复**。

- 每个需求点完成后运行测试/构建/lint（本项目 UI 类：构建 + 类型检查 + 界面走查清单）。
- 失败时："先告诉我问题在哪里，不要急着改。"
- 让 Agent 输出交付总结，四要素：**修改文件 / 修改原因 / 验证命令 / 验证结果**。

### 4.6 高风险操作禁令

- 删除文件、批量重命名、改数据库、发布上线、安装依赖：**先解释"这个命令会做什么？有没有风险？"人工确认后才执行**。
- 用 Hook 兜底自动拦截（见 6.3 节）：rm -rf、git reset --hard、git push --force、curl | sh 等。

### 4.7 本项目特有的控制点

1. **文案一致性**：界面文字必须与需求文档逐字一致（语音台词、按钮名、状态短语、状态色语义）。这是本项目需求文档最核心的资产，也是最容易被 Agent 悄悄改写的地方。
2. **多场景并行风险**：场景 1/2 结构相似但文案不同，Agent 极易"复制粘贴后漏改"。要求每个场景的文案引用自文档对应章节，验收时两场景交叉比对。
3. **待确认事项冻结**：需求文档第 10 节的未裁决项未定前，涉及部分（场景名称、按钮文案）标记为"阻塞"，不允许实现。
4. **范围边界**：**场景三「立体融合攻坚」与全部三维能力已放弃**（见需求初稿附录 A），Agent 不得依据 `需求图与描述/场景3/` 或旧版"三场景"表述自行实现；发现文档间范围冲突应立即上报，不得自行选择其一。

## 5. 流程控制：一次任务的标准流程（防错主线）

### 5.1 五步核心循环（jspang 文章）

```
读代码/读文档 → 制定计划 → 修改文件 → 运行命令 → 验证结果
```

### 5.2 文档驱动版完整流程（带三道门禁）

```
① 领任务：从 03-任务清单.md 取一个需求编号（如 R-场景1-T4）
      ↓
② 读文档：Agent 读取需求文档对应章节 + 设计文档 + AGENTS.md
      ↓
③ 复述确认：Agent 用 3-5 行复述"要做什么、验收标准是什么"
      ↓
④【门禁1·计划确认门】Agent 给出计划（文件清单/改动点/验证方式）
      人工确认 → 不通过则纠正，返回 ③
      ↓
⑤ 实施：Agent 按计划修改，保持最小改动
      ↓
⑥【门禁2·验证门】运行构建/测试/lint + 界面走查
      ↓  失败 → Agent 分析原因再修（先分析后动手）
⑦ diff 三问 + Agent 交付总结（文件/原因/命令/结果）
      ↓
⑧【门禁3·验收门】人工按 04-验收标准.md 勾选核对
      ↓  不通过 → 把新规则写进 AGENTS.md，返回 ⑤
⑨ 提交：一次任务一个 commit，信息挂需求编号；Agent 在开发日志追加记录
      ↓
⑩ 文档回写：需求有变/决策产生 → 更新变更记录或 ADR（人工）
```

### 5.3 每次任务的一句话模板

> 启动："任务编号 R-xxx。先读 docs/01-需求文档.md 第 x 节和 AGENTS.md，复述需求与验收标准，然后给出计划，**不要开始改代码**。"
> 收尾："查看本次 diff 并做三问自检；运行构建/测试；输出交付总结（修改文件/原因/验证命令/结果）；按 commit 规范提交。"

### 5.4 界面文案核对（本项目专用流程）

每个界面完成后，让 Agent 用**原文比对**方式自检：

> "逐条核对本界面所有可见文字（按钮、标签、语音台词、状态短语）与需求文档对应章节是否逐字一致，输出差异清单：需求原文 vs 实现文字。不得自行修改任何措辞。"

必要时做成 Skill 反复使用（见 6.2）。

## 6. 工具化落地：AGENTS.md / Skills / Hooks / Subagents

### 6.1 AGENTS.md 模板（本项目的骨架）

```markdown
# AGENTS.md — 任务管理系统项目规则

## 项目一句话
平板端无人机任务管理系统前端（原型/演示），需求唯一事实源：docs/01-需求文档.md。

## 技术栈与命令
- 框架：<待设计文档确定，如 Vue3+TS>
- 启动：npm run dev；构建：npm run build；检查：npm run lint

## 目录结构
见 FilesTree.md；UI 组件按需求编号命名（如 Scenario1T4TargetDetail）。

## 工作流规则
1. 每次任务先复述需求+给出计划，人工确认前不得改代码。
2. 一个任务一个 commit，信息格式：`feat(R-场景1-T4): 目标详情界面`。
3. 改动最小化，禁止顺手重构；计划外改动必须先询问。
4. 完成后必须：diff 三问自检 → 跑验证命令 → 输出交付总结 → 追加开发日志。

## 界面文案铁律
- 所有按钮、标签、语音台词、状态短语必须与 docs/01-需求文档.md 逐字一致。
- 禁止润色、改写、新增、删减任何文案；发现文档问题只报告，不改文档。

## 禁做清单（违反即停止）
- 修改 docs/ 下需求文档、设计文档、AGENTS.md 本身。
- 执行删除/重命名/依赖安装/发布类命令（需人工批准）。
- 自行裁决需求文档第 10 节"待确认事项"。
- 把演示数值（92%、87%、目标003）写死为常量逻辑。

## 引用规范
代码注释与 commit 中引用需求编号 R-{场景}-{T阶段}，如 R-场景1-T4-界面2。
```

### 6.2 Skills（把重复流程固化）

- **requirement-check Skill**（需求核对）：按 5.4 节流程比对界面文案与需求文档，输出差异清单。
- **ui-acceptance Skill**（界面验收）：按 04-验收标准.md 逐项勾选走查，输出通过/不通过与截图说明。
- **daily-log Skill**（开发日志）：固定输出"今日完成/遇到的问题/明日计划/变更文件"。
- 规则：**当你第三次输入同一套提示词时，就把它做成 Skill**（jspang 原文）。

### 6.3 Hooks（把规则变成自动执行）

- **PreToolUse 命令检查**：拦截 rm -rf、git reset --hard、git push --force、curl|sh、删除 .env 等（jspang 文章提供了完整 `check_command.py`，可直接复用）。
- **提交前校验（可选）**：commit 信息必须含 R- 编号，否则阻止提交。
- **任务结束钩子（可选）**：自动提醒"是否已输出交付总结、是否已追加开发日志"。

> 提醒：Hooks 依赖 Python 脚本，先掌握 AGENTS.md 与 Skills，确有"必须自动执行"的规则再加 Hooks。

### 6.4 Subagents（并行探索可以，并行写代码谨慎）

- 适用：多场景**并行实现后交叉审查**、需求文档一致性审查（多个 agent 分别核对场景 1/2 文案，最后汇总）。
- 提示词要点：明确"并行"、几个 agent 各负责什么、等待全部完成再汇总、规定输出格式、**先不要修改文件**。
- 禁止：让多个 agent 同时写代码——文件冲突合并成本高。

### 6.5 Plugins（团队化阶段再考虑）

当上面这套（AGENTS.md + Skills + Hooks）需要在多台机器/多人间复用，再打包成 Plugin（`.codex-plugin/plugin.json`）分发。个人项目阶段不必提前做。

## 7. 持续迭代与可回溯

### 7.1 迭代模型：文档先行，小步闭环

```
需求文档 v1 → 任务清单 → 实现 → 验收 → 反馈/新需求
     ↑                                    ↓
  人工更新文档 v1.1 ←—— 变更记录/ADR ←—— 决策与变更
```

- 需求先改文档，再改代码；**永远让代码追文档，不让文档追代码**。
- 每完成一个 T 阶段（T0→T7）打一个里程碑 tag：`v0.1-T0`、`v0.2-T1`……可随时回退到任意界面阶段。

### 7.2 回溯的三层机制

| 层 | 机制 | 用途 |
| --- | --- | --- |
| 代码层 | Git 小步提交，commit 挂需求编号 | `git log --grep="R-场景1-T4"` 即得该需求全部改动 |
| 文档层 | 文档入 git + 05-变更记录.md + decisions/ADR | 回答"这个需求为什么变成这样、谁拍的板" |
| 过程层 | 开发日志（Agent 每次任务追加：计划/改动/验证/结果） | 回答"当时怎么做的、验证过没有" |

### 7.3 追溯纪律（三条铁律）

1. **一个 commit 只对应一个需求编号**，禁止大杂烩提交。
2. **文档与代码同步提交或先行提交**：改需求必须同 commit 更新需求文档/变更记录。
3. **踩坑必回写**：每次 Agent 犯错，把教训写成一条新规则进 AGENTS.md（错误不重复第二次，就是最快的迭代）。
